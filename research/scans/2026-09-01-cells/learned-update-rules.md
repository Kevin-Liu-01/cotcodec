# Collision scan — learned update rules (cell: `learned-update-rules`)

**Scan date:** 2026-09-01 · **Prior sweep cutoff:** 2026-08-10 · **Owner:** CoTCodec frontier program
**Question:** Is "port HOW a model updates (its update rule / inner optimizer), not WHAT it stores" an unclaimed axis?
**Short answer:** No direct prior art found through 2026-09-01 for *cross-operator-family transfer of a learned inner-loop update rule at LM scale* under the coverage below — but every neighbouring axis is occupied, several by post-2026-08-10 work, and two 2026 negatives (SR-TTT v2, "Beyond Perplexity") set the evidentiary bar. Details, queries, and limits follow.

Status labels: **[PR]** peer-reviewed venue confirmed; **[FP]** first-party preprint/README/blog claim, not independently replicated; **[NEG]** negative result or retraction.

## 3. Open gaps (each was searched explicitly and came back empty or adjacent-only)

**G1. Cross-operator-family transfer of a *learned* inner-loop update rule at LM scale.** Meta-learn the fast-weight update rule (step-size/preconditioner/erase-write policy as a small network) on one operator family (e.g., a TTT-MLP or GDN layer) and evaluate it frozen on a different family (softmax-window TTT, KDA, masked-diffusion denoiser), with matched state size and derived-rule baselines (KLA, OSDN, P-DeltaNet).
- *Why open:* Modular TTT factorizes but never transfers; MetaNCA/UNF transfer only on 2M-param feedforward nets; FedNL shares rules across clients of the same architecture; the ICL-theory cluster (F43, F57, F53) predicts the implicit rule differs by family, so the result is uncertain in either direction.
- *Evidence:* arXiv API `abs:"update rule" AND ("across architectures" OR "architecture-agnostic" OR portable)` → 1 hit (federated learning, irrelevant); HF-papers index "portable update rule", "inner loop optimizer transfer test-time training", "meta-learning update rule across model families" → no relevant hit; WebSearch "meta-learned update rule transfers across architectures transformer state space model 2026" → summaries + Priming (weights) only.
- *Kevin advantage:* the 340M–1.3B / 15–100B-token regime used by GDN-2, QED, TTCD and Modular TTT fits one 8×H100 node with the existing digest-pinned Slurm/checkpoint harness; open FLA-style kernels and Modular-TTT-style primitives exist; parallel translation data gives a paired "same content, different surface form" probe for whether a ported rule preserves what is stored.

**G2. Learned optimizers (Celo2/ELO class) evaluated on or meta-trained with non-transformer targets (Mamba/DeltaNet/diffusion LM).**
- *Why open:* ELO's README task list and Celo2's abstract cover MLP/ViT/ResNet/GPT-2/GPT-3-XL only; no SSM, delta-rule or diffusion target anywhere; VeLO/μLO negatives show generalization is fragile.
- *Evidence:* arXiv API `abs:"learned optimizer" AND (Mamba OR "state space" OR diffusion)` → 25 hits, none relevant; HF-papers "learned optimizer Mamba state space", "learned optimizer diffusion model training", "learned optimizer masked diffusion language model" → none; GitHub `learned optimizer mamba` → 0 repos.
- *Kevin advantage:* PyLO ships drop-in PyTorch LOs with HF weights (ELO-Celo2, VeLO); Mamba-130M, Kimi-Linear-48B-A3B and LLaDA-8B are already pinned locally; ELO's 124M–350M FineWeb protocol costs <7 GPU-hours to meta-train — a fully reproducible, cheap experiment whose negative result is informative.

**G3. A meta-learned optimizer for LoRA/post-training of pretrained LLMs (2026).**
- *Why open:* Narrowing the Focus (2024) is vision-only; Optimizer-Model Consistency shows the fine-tuning optimizer matters for forgetting; no 2026 work meta-learns the LoRA update rule for LLMs.
- *Evidence:* arXiv API `abs:"learned optimizer" AND (LoRA OR "fine-tuning" OR finetuning)` → 25 hits, none relevant (L-SR1 is mesh recovery); HF-papers "learned optimizer LoRA fine-tuning" → only LoRA variants; WebSearch for this probe was blocked by the search budget.
- *Kevin advantage:* Tinker managed LoRA/RL across Kimi-K2.6, Qwen3.5, GLM-5.3, DeepSeek-V3.1 gives multi-family targets; **feasibility caveat:** it is unverified whether Tinker exposes custom optimizer steps (vs. fixed Adam `optim_step`); if not, the local 8×H100 node with Qwen3.5-4B/Qwen3-0.6B-Base is the fallback.

**G4. Parallel-translation data as a meta-training or evaluation objective for update rules (translation-equivariant test-time learning).**
- *Why open:* No paper uses paired translations to constrain or evaluate a fast-weight update (e.g., requiring a sentence and its translation to induce the same state write, or measuring recall across languages after a write).
- *Evidence:* arXiv API `(abs:multilingual OR abs:"parallel data" OR abs:translation) AND (abs:"test-time training" OR abs:"meta-learned update")` → 4 irrelevant hits; HF-papers "multilingual test-time training", "cross-lingual meta-learning parallel data", "translation test-time adaptation language model" → only test-time *scaling* for MT and multilingual reasoning.
- *Kevin advantage:* General Translation's production parallel multilingual data is exactly the paired corpus required and is not available to the groups above.

**G5. Behavioral, causality-verified evaluation of update-rule variants (GDN-2/QED/E²-TTT/Modular-TTT class) for memory claims.**
- *Why open:* Beyond Perplexity covers LoRA-based TTT on Qwen3 only; SR-TTT v2 covers one architecture; rule papers report perplexity, RULER/NIAH and MC accuracy, never recall/locality/retention after context removal under startup-causality perturbation.
- *Evidence:* arXiv API `abs:"test-time training"` newest 25 and HF-papers "test-time training update rule" → no paper applying a behavioral memory protocol to delta-rule/TTT update-rule variants.
- *Kevin advantage:* the repo already specifies startup-causality perturbations, exact-generation matching and storage/addressing/readout decomposition (SR-TTT lesson) plus a CPU paired oracle; 340M-scale sweeps fit the node.

**G6. Distilling a pretrained transformer's implicit ICL update (its HOW) into an explicit recurrent fast-weight rule, rather than distilling weights.**
- *Why open:* Priming/linearization port weights; Algorithm Distillation goes algorithm→transformer; "Can GD simulate prompting" converts context→gradient within one model; nothing fits a recurrent update rule to reproduce a transformer's in-context state changes.
- *Evidence:* HF-papers "update rule distillation recurrent" → RL/on-policy distillation only; WebSearch probe for this exact phrasing was blocked by the budget (not executed) — coverage is therefore weaker for G6 than for G1–G5.
- *Kevin advantage:* Priming's Apache-2.0 conversion code, pinned Qwen3-0.6B-Base/Qwen3.5-4B checkpoints, and the per-family ICL theory (GD emulation vs online GD vs Bayes filter) give falsifiable predictions; 8×H100 suffices for ≤4B conversions.
